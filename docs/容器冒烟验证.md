## 🐳 容器运行态验证（CI smoke-run）

> 此前 README 写「本机无 Docker，容器运行态未验证」。
> 有了 CI 之后这个缺口已被补上—— GitHub 的 ubuntu runner 自带 Docker。

**Actions 链接**：[runs/39015038437](https://github.com/XiaoS001/sre-observability-platform/actions/runs/39015038437)

### CI 的三个 job

```
test → docker-build → smoke-run        （链式依赖，前一步过了才跑下一步）
```

| job | 验证什么 | 结果 |
|---|---|---|
| `test` | pytest 257 条 + 编译检查 + 密钥扫描 + 测试库隔离 | ✅ success |
| `docker-build` | 构建镜像并推送 GHCR | ✅ success |
| `smoke-run` | **容器真跑起来** | ✅ success |

### smoke-run 实际验证的 5 项

| 项 | 实测输出 |
|---|---|
| 容器能启动 | `✅ 健康检查通过（第 2 次探测）` |
| **非 root 运行** | `容器内用户: appuser (uid=1001)` |
| entrypoint.sh 真能执行 | `✅ 容器以合法配置启动` |
| 挂载卷 + AI 工具查库 | `query_check_records -> True`（返回结构化结果，非 `db_error`） |
| 业务路由与鉴权 | `✅ /status 200` · 未登录 `/api/rules` → **401** |

> 🔴 **这些是容器里的真实输出**，不是本机模拟。
> 意味着「镜像能 build」到「容器能 run」之间的差距已被验证。

### smoke-run 抓到的一个真 bug

第一次运行**红了**：

```
OCI runtime create failed: runc create failed:
unable to start container process: error during container init:
exec: "./entrypoint.sh": permission denied
```

**根因**：Windows 上 git 的 `core.fileMode=false`，不保存可执行位，
仓库里 `entrypoint.sh` 是 `100644`。Dockerfile 直接
`ENTRYPOINT ["./entrypoint.sh"]` 就没权限跑。

**修法（两道保险）**：

1. **Dockerfile 显式 `chmod +x /app/entrypoint.sh`** ← 关键
   构建期赋权，不依赖仓库权限位，任何环境都成立
2. `.gitattributes` 声明 `/entrypoint.sh mode=100755`
   让支持 `fileMode` 的环境也带上执行位

并补了 4 条测试锁住这个坑（Dockerfile 必须 chmod、.gitattributes 必须声明
mode、必须对 `*.sh` 声明 `eol=lf`、源文件不能含 CRLF）。

> **这个 bug 只有真跑容器才会暴露** —— 「能 build」不等于「能 run」，
> 这正是加 smoke-run job 的价值。
