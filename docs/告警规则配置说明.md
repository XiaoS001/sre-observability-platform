# 告警规则配置说明 · RMB03

> 实现：`alerts.py`　求值入口 `evaluate_rules()`，去重入口 `is_in_cooldown()`

---

## 一、三种规则类型

| `rule_type` | 含义 | `threshold` 单位 | 触发条件 | 需要的数据 |
|---|---|---|---|---|
| `consecutive_failure` | 连续失败 N 次 | 次 | 连续失败数 **≥** N | 最近若干条记录 |
| `availability` | 可用率低于 X% | 百分比 | 窗口可用率 **<** X | 窗口内全部记录 |
| `p95_latency` | P95 响应超 Y ms | 毫秒 | P95 **>** Y | 窗口内**成功**记录 |

### 1. `consecutive_failure` · 连续失败 N 次

从最新记录往回数，**遇到一次成功即归零**。

```
记录（新→旧）：F F F S F
                  └─┬─┘
连续失败 = 1（数到第一次成功就停）
```

阈值示例：`threshold=3` → 连续 3 次失败才告警。

> 🔴 **「连续」不是「最近 N 次里有 N 次」** —— 后者会在服务抖动时误报。

### 2. `availability` · 可用率低于 X%

窗口内 `success / total × 100`，默认窗口 **30 分钟**。

阈值示例：`threshold=95` → 可用率跌破 95% 告警。

> 🔴 **无数据时返回 `None`（不判定），不返回 0%**。
> 返回 0% 会让刚接入还没巡检的目标立刻误报一堆告警。

### 3. `p95_latency` · P95 响应超 Y ms

窗口内**成功**记录的耗时排序取第 95% 位，默认窗口 **30 分钟**。

阈值示例：`threshold=500` → P95 超过 500ms 告警。

> 🔴 **只看成功记录**：失败请求的耗时（往往是超时）不代表服务响应能力，
> 混进来会把 P95 彻底带偏。

SQLite 没有 `percentile` 函数，实现为「按耗时升序取第 `int(n*0.95)` 条」。
数据量小，内存排序更直观，也避免 SQL 方言差异。

## 二、阈值单位随类型变化（设计取舍）

三种规则共用一张 `alert_rule` 表，`threshold` 是 `FLOAT`。
**单位不同是刻意的**：如果拆成三张表，求值入口就要写三遍；
现在共用一个 `evaluate_rule()`，新增类型只需加一个分支。

代价是**失去类型约束** —— `consecutive_failure` 的 threshold 填 0.5 没有意义。
用入口校验（见下）挡住。

### 创建规则时的校验

| 校验 | 拒绝理由 |
|---|---|
| `rule_type` 必须在三种取值内 | 未知类型会被 `evaluate_rule` 返回 None 静默跳过 |
| `target_id` 必须存在 | 否则规则永远不触发，且看不出原因 |
| `threshold` 必须是数字 | — |

> ⚠️ 「未知 rule_type 静默跳过」是刻意的：数据库里有一条脏规则时，
> 整个告警循环不能因此崩掉。`tests/test_alerts.py::test_evaluate_rules_ignores_unknown_rule_type` 锁住这个行为。

## 三、冷却期去重（重复抑制，不是持续时长）

### 两种语义的区别

| 概念 | 含义 | 对第一次告警的影响 |
|---|---|---|
| **for 持续时长** | 条件必须**连续成立** N 秒才触发 | 🔴 **会延迟第一次告警** |
| **冷却 / 重复抑制** ✅ | 触发后 N 秒内不再重复触发 | ✅ **不影响第一次** |

本项目实现的是**重复抑制**：从未告警过 → `is_in_cooldown` 返回 `False` → 首次必然创建。

### 去重键

`(rule_id, target_id)` —— 同一规则对同一目标，在冷却窗口内只留一条告警。

- 不同规则互不影响（A 规则的告警不会压掉 B 规则的）
- 不同目标互不影响
- 查的是**最近一条**告警，不是最早那条

### 时间线示例（冷却 300 秒，规则「连续失败 2 次」，目标 interval 60 秒）

| 时刻 | 事件 | 告警表 |
|---|---|---|
| t=60s | 第 1 次失败 | 无（还差 1 次） |
| **t=120s** | **第 2 次失败 → 触发** | **✅ 1 条** |
| t=180s | 第 3 次失败 | 无（冷却中 —— 这正是去重该有的表现） |
| t=240~360s | 第 4~6 次失败 | 无（冷却中） |
| t=420s | 第 7 次失败（距上次告警 300 秒） | ✅ 新增 1 条 |

### 边界行为

判定用 **`<`**：`elapsed 恰好等于 cooldown` 时**允许**再次告警。

> 理由：「恰好到期即可再次告警」比「再多等一秒」更符合直觉，
> 而且后者会让运维以为规则没生效。

这个边界有**毫秒级双向夹逼**测试锁住（60.000 秒允许 / 59.999 秒抑制）：

```python
def test_cooldown_boundary_allows_new_alert(app_context):
    rule = _make_rule()
    anchor = datetime(2026, 10, 16, 12, 0, 0)      # 固定时刻，不用 now()
    _make_alert(rule, triggered_at=anchor - timedelta(seconds=60))
    assert is_in_cooldown(rule.id, rule.target_id,
                          now=anchor, cooldown_seconds=60) is False

def test_cooldown_just_inside_window_is_suppressed(app_context):
    rule = _make_rule()
    anchor = datetime(2026, 10, 16, 12, 0, 0)
    _make_alert(rule, triggered_at=anchor - timedelta(seconds=59, milliseconds=999))
    assert is_in_cooldown(rule.id, rule.target_id,
                          now=anchor, cooldown_seconds=60) is True
```

> 🔴 **必须两侧都写**。单靠一条锁不住比较符 ——
> 若 `now` 用真实时钟，两次 `datetime.now()` 之间有毫秒漂移，
> 名义「恰好 60 秒」实际是 60.0036 秒，`<` 与 `<=` 结果相同。
> （这个坑真踩过：变异测试把 `<` 改成 `<=` 时最初**没被抓到**。）

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `RMB03_ALERT_COOLDOWN_SECONDS` | `300` | 冷却窗口。5 分钟是常见的抑制窗口 —— 60 秒会导致故障期间刷屏 |

## 五、通知

### 投递流程

```
告警创建 → notify()
           ├─ webhook  → send_webhook()  → POST JSON
           └─ email    → send_email()    → 占位实现
           每条结果落库 notification（成功失败都记）
```

webhook 负载：

```json
{
  "text": "[demo-支付回调] demo-连续失败告警（3 次）: ...",
  "alert_id": 1, "rule_id": 1, "target_id": 5,
  "reason": "connect",
  "observed_value": 5.0, "threshold": 3.0,
  "triggered_at": "2026-10-16 19:08:13"
}
```

### 🔴 通知失败绝不抛出

三层兜底：

1. `send_webhook` 内部 `try/except` 捕获网络异常与 `HTTPError`
2. `_deliver` 再兜一层
3. 无论成败都写 `notification` 表

**理由**：平台对外承诺的是「告警被记录」，不是「通知一定送达」。
通知失败应表现为一条 `success=false` 的记录，而不是整个告警流程崩掉。

### 邮件通道是占位

按任务单边界「先做 webhook + 邮件占位，不接真实短信/电话」，
`send_email()` 只把「该发什么」组织好并落库，**不实际发信**。

## 六、一轮告警流程

```python
def run_alert_cycle(now=None, cooldown_seconds=None):
    for rule, observed, detail in evaluate_rules(now=now):
        alert = create_alert(rule, observed, detail,
                             now=now, cooldown_seconds=cooldown_seconds)
        if alert is not None:      # None = 冷却中
            notify(alert)
```

由 `run_due_targets()` 在**每轮巡检之后**调用 —— 规则要基于刚落库的记录判断。

## 七、排障

| 现象 | 排查方向 |
|---|---|
| 规则不触发 | ① 规则 `enabled` 是否为 true ② `availability`/`p95` 类型是否**窗口内无数据**（返 None 不判定）③ 目标是否 `enabled` |
| 告警不重复（符合预期） | 看 `alert` 表最新 `triggered_at`，确认是否在冷却窗口内 |
| `consecutive_failure` 不触发 | 「连续」遇成功即归零。检查最近是否中间插入了成功记录 |
| 通知发不出去 | 查 `notification` 表的 `error_msg`；webhook 未配置时也会记一条失败 |
| 指标 reason 与日志对不上 | 两者共用 `_classify_failure`，若不一致说明有绕过该函数的写入路径 |
